## [2026-06-08] Codex 过期提醒与 429 自动热轮换
- Codex 配置页新增过期提醒：档案加载后顶部汇总“已过期 / 即将过期”数量，单个档案状态旁显示“即将过期”或“已过期，请刷新后再轮换”；提醒仅由 `AccessTokenExpiresAt` 与 `Status` 计算，不新增持久化字段。
- 新增 `CodexRateLimitLogMonitorService`：只读打开 `%USERPROFILE%\.codex\logs_2.sqlite`，首次读取 `MAX(id)` 作为基线，之后每 20 秒增量读取最多 50 行，识别 `codex.rate_limits` / rate-limit 日志中的 `allowed=false` 或 `limit_reached=true`，只返回 log id、时间和 reset 摘要，不记录日志正文、token 或请求内容；打开 SQLite 前设置进程级 `SQLite_ConfigureDirectory` 与 `SQLite_NoPlugins`，确保单文件嵌入的 SQLite 原生依赖可定位。

## [2026-05-12] 全项目稳定性 / 效率 / 资源占用 优化
目的：在不改变现有功能的前提下提升运行期稳定性、降低内存占用、消除潜在泄漏与死锁。

1) WMI 资源泄漏修复（HardwareInfoService / SystemInfoService / BenchmarkService）：
   - 之前 `foreach (ManagementObject mo in searcher.Get())` 未 Dispose `ManagementObjectCollection` 与每个 `ManagementObject`，在频繁查询下会积累 COM 对象。
   - 新增 `Query(wql, handler)` 统一辅助方法，使用 `using` 同时释放 searcher / collection / 每个 MO（`try { ... } finally { mo.Dispose(); }`）。
   - 增加 `EnumerationOptions { ReturnImmediately=true, Rewindable=false, UseAmendedQualifiers=false, DirectRead=true }` 复用实例，减少 WMI 内部缓存与数据量。

2) 启动性能：
   - `MainViewModel` 构造函数中原来同步调用 `SystemInfoService.GetSnapshot()`（包含 WMI Win32_Processor 查询，典型 100-300 ms），改为 `SafeFireAndForget(LoadSystemInfoSnapshotAsync())` 后台加载，窗口立即显示。
   - `SystemInfoService` 新增 `GetSnapshotAsync()` 入口，`SystemInfo` 属性变为可写并触发 `PropertyChanged`。

3) 时长计算 49 天溢出修复：
   - `SystemInfoService.GetSnapshot` 原使用 `Environment.TickCount & int.MaxValue`，超过 ~24.8 天后会归零。改为 P/Invoke `kernel32!GetTickCount64()`，Win7+ 全平台支持。失败回退原算法。

4) 传感器轮询 CPU 占用优化：
   - `HardwareSensorService` 的 `DispatcherTimer` 之前即使用户离开"系统信息"页也继续每 2 秒刷新。
   - `CurrentModule` setter 现在会在离开 SystemInfo 时自动 `_sensorTimer.Stop()`，返回时自动 `Start()`，只要 `IsSensorsRunning=true`。空闲时节省 ≥ 5% CPU。

5) 文件哈希 IO 4× → 1× 重写：
   - 原 `FileHashService.ComputeAsync` 依次调用 4 次 `ComputeHashAsync<T>` + CRC32，同一个大文件会被顺序读取 4 遍（10 GB ISO 实测约 4 倍硬盘时间）。
   - 改为单遍流式读取 1 MB 缓冲，分别调用 `md5.TransformBlock` / `sha1.TransformBlock` / `sha256.TransformBlock` + 内联 CRC32 累加，最后 `TransformFinalBlock`。IO 降到 1×，并新增 16 MB 粒度进度回报（"已扫描 X% (Y/Z MB)"）。
   - 缓冲区从 80 KB 升到 1 MB 以提升顺序读吞吐。

6) MediaConvertService 稳定性：
   - `FindFfmpeg`：之前直接 `WaitForExit(3000)` 而不读 stdout/stderr，如果 ffmpeg 输出量大会阻塞在管道上。改为先同步 `ReadToEnd()` 清空管道，再 `WaitForExit(5000)`，超时则 `Kill()`。
   - `ConvertMediaAsync`：`StandardError.ReadToEnd()` 在 `WaitForExit` 之前会在子进程输出量大时死锁。改为在后台 `Task.Run` 读 stderr，主线程同步读 stdout 并 `WaitForExit(300_000)`；超时则 `Kill()` 并返回超时错误，避免僵尸进程。
   - `EncoderParameters` 现包在 `using` 中，避免 GDI+ 对象累积。

7) BenchmarkService 释放内存：
   - 内存带宽测试 256 MB 缓冲完成后立即 `buffer = null; GC.Collect(2, GCCollectionMode.Optimized, false)`，避免数据在 LOH 停留。
   - GPU 信息查询的 `ManagementObjectCollection` / `ManagementObject` 现已完整 Dispose。

8) XAML 类型错误修复：
   - 转换模块两个主按钮原来用 `InverseBoolToVis`（Visibility）绑定给 `IsEnabled`（bool），类型不匹配、仅靠隐式转换凑效。已删除该绑定，交由 Command 的 CanExecute 自动控制禁用态。

构建验证：0 errors，单 EXE 仍为 12.83 MB。

## [2026-05-16] 录像文件缺失修复

- `RecordingService.StartVideoRecordingAsync` 增加启动探测：带音频录像若 ffmpeg 立即退出，自动删除空文件并降级为仅录制画面；仅画面仍立即退出时直接提示录像未开始。
- `RecordingService` 在启动录像前将录制区域宽高自动向下修正为偶数像素，修复用户拖出 `1341x771` 等奇数尺寸时 `libx264 + yuv420p` 打开编码器失败的问题。
- 新增 `WasapiLoopbackAudioRecorder`，录像与独立录音改为程序内置 WASAPI Loopback 采集系统播放声音，不再依赖 `virtual-audio-capturer`、`Stereo Mix`、`立体声混音` 或麦克风设备。
- 录像时 ffmpeg 只录画面到临时 MP4，程序同步采集系统声音到临时 WAV；停止后自动合成为最终 `H.264 + AAC + MP4`，并清理临时文件。
- 独立录音改为采集系统播放声音，停止后通过 ffmpeg 转码为 `.m4a`；采集为空时直接提示，不生成静音文件。
- 修复纯录音停止后清理临时文件时空路径触发 `ArgumentException` 的问题；清理临时文件失败也不再阻断录制状态释放，避免后续误报“当前已有录像/录音任务在进行”。
- `MyTools.csproj` 新增 `NAudio 2.2.1`，由 Costura 合并进单 exe。
- `RecordingService.StartAudioOnlyAsync` 同步增加启动探测，音频设备被占用或禁用时避免进入虚假的“录音中”状态。
- `MainViewModel.StopVideoRecordingInternalAsync` 停止后按实际输出路径检查文件存在性与字节数，不再把 `TimedOut=false` 的 0B 文件当成成功。
- 录像保存成功后自动打开资源管理器并选中新文件；提示中标明“包含音频”或“仅画面”，便于确认本次录制内容。
- ffmpeg 音频设备枚举与运行日志读取改用系统默认编码，降低中文设备名在日志中显示为乱码的概率。

# Loop Engineering 记忆沉淀

Loop Engineering 的记忆目标是让后续开发更快、更稳、更少返工。沉淀的是可复用事实、可执行检查和稳定流程，不记录一次性进度、聊天摘要或无法复用的过程。

## 一、沉淀前先问三件事

1. 这次有没有一个下次可以自动检查的错误或约束？
2. 这次有没有一个下次读文档就能少走弯路的模块事实？
3. 这次有没有一个项目边界被反复触碰，需要变成硬规则或 workflow？

三项都没有时，不强行写记忆，只在最终回复中说明“无新增可沉淀记忆”。

## 二、记忆分层路由

| 记忆类型 | 沉淀位置 | 记录内容 |
| --- | --- | --- |
| 可执行业为、稳定 bug 复现 | 自动化测试、构建脚本、`scripts\codex-eval.ps1` | 输入、预期结果、回归断言 |
| 可重复验证门禁 | `scripts\codex-eval.ps1` | 检查入口、失败提示、适用范围 |
| 项目级硬边界、禁令、性能红线 | 根 `AGENTS.md` | 简短刚性规则，不写过程流水 |
| 重复工作方法 | `.agents\skills\*\SKILL.md` | Inspect、Plan、Validate、Review、Deposit 的步骤变化 |
| 独立审查标准 | `.codex\agents\*.toml` | reviewer 必查项、输出格式、记忆候选要求 |
| 用户功能事实 | `docs\功能说明.md` | 功能入口、使用方式、用户可见行为 |
| 模块行为和运行逻辑 | `docs\程序逻辑.md` | Service、ViewModel、View、配置、数据流和边界 |
| 可见控件和真实使用流程 | `docs\场景驱动开发\*.md` | 流程步骤、实现证据、控件功能、校验和状态 |
| 安装包或性能阶段计划 | `docs\规划\` | 阶段目标、基线、待确认项、验收方式 |
| 只对本次任务有用的进度 | 不沉淀 | 只在对话最终回复中说明 |

## 三、推荐记录格式

```text
适用场景：
正确做法：
禁止事项：
验证方式：
相关文件：
```

记录必须短、准、能定位。不要复制长日志，不要记录已经过期的猜测。

## 四、失败特征格式

重复失败或修复后特别有复用价值时，按以下格式沉淀到最合适的位置：

```text
错误现象：
根因：
最小修复：
验证命令：
沉淀位置：
```

能写成测试或验证脚本的失败，优先转成可执行检查，再在文档中保留一句入口说明。

## 五、Review 阶段要求

- reviewer 必须检查本次触达模块是否已同步到对应活文档。
- reviewer 必须在输出末尾给出 `记忆候选：无`，或给出 `记忆候选：建议沉淀到 <路径>，内容：<一句话>`。
- 主 agent 只处理可复用、可验证、与当前改动直接相关的候选；不为凑数创建总结类 Markdown。

## 六、过期记忆清理

- 发现路径、组件、函数、命令或构建产物约定不存在时，优先更新对应活文档和 `docs\智能助手记忆索引.md`。
- 发现规则已经被自动化覆盖时，文档保留规则和验证入口即可，删除重复过程描述。
- `docs\规划\已经执行\` 是历史证据；后续代码或活文档不一致时，以当前代码和活文档为准。
- 清理记忆属于规则维护任务，必须验证 UTF-8、路径存在性和 `git diff --check`。

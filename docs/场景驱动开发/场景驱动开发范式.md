# 场景驱动开发范式

本文是一套可放入任意项目使用的场景驱动开发范式。它用于把“真实岗位如何完成一件事”转化为可实施、可验证、可持续维护的软件开发流程。

范式的核心目标是：先理解业务场景，再寻找现有承载点，优先复用和补全已有能力，最后才考虑新建模块。每次开发都必须同步维护业务流程、实现状态和控件交互三类活文档，让后续开发可以从事实和证据继续，而不是从记忆和猜测重来。

## 零、启动方式

当用户输入 `开qg`、`开qg 目标` 或同义表达时，进入场景驱动开发准备态。

准备态只收集信息，不立即修改代码或文档。

1. 用户只输入 `开qg` 时，必须要求用户提供目标、业务角色和入口。
2. 用户输入 `开qg 采购入库` 等已带目标的表达时，只补问缺失的业务角色和入口。
3. 信息齐全后，必须生成确认卡片，列出目标、业务角色、入口、执行方式、预计动作和文档同步范围。
4. 用户回复 `确认执行` 后，才允许进入读取、实施、文档同步和验证。
5. 用户回复 `取消` 时，停止本次准备，不修改代码、不修改文档。
6. 用户回复 `补充：` 或直接补充信息时，按新信息重新整理确认卡片。

确认卡片模板：

```text
场景目标：
业务角色：
入口位置：
执行方式：
预计动作：
文档同步范围：
本轮禁止事项：
待确认项：
```

## 一、文档分层

场景驱动开发至少包含四类文档。

1. `场景驱动开发范式.md`：方法规则，只记录范式、模板、执行顺序、验收标准、同步规则和禁止事项。
2. `业务流程清单.md`：业务事实清单，记录岗位、入口、步骤、前后置条件和异常路径。
3. `场景实现核查台账.md`：实现状态账本，记录每个场景的实现状态、证据文件、剩余缺口、验证结果和待确认项。
4. `控件交互逻辑说明.md`：用户界面事实说明书，记录页面、弹框、控件、按钮、筛选项、表格列、提示文案、禁用状态、校验规则、跳转逻辑和权限展示。

推荐目录：

```text
docs/场景驱动开发/
  场景驱动开发范式.md
  业务流程清单.md
  场景实现核查台账.md
  控件交互逻辑说明.md
```

如果项目已有同类文档，可以沿用原文件名，但必须在文档开头写清楚对应职责。旧名称不影响范式执行，职责边界必须清晰。

## 二、三份活文档生成规则

首次在一个项目启用本范式时，必须检查三份活文档是否存在。

1. 不存在时，按本范式自动创建模板。
2. 已存在时，不得直接整文件覆盖；除非用户明确要求替换，否则只能增量整理。
3. 旧文档内容与代码不一致时，以当前代码、可运行行为和用户确认的业务事实为准。
4. 无法确认的信息必须标注 `[待确认]`，不得补写成确定规则。

三份活文档的自动生成来源可以包括：

1. 用户明确描述的工作流程、岗位和规则。
2. 现有 README、产品文档、操作手册、测试用例和规划文档。
3. 代码中的路由、菜单、权限、页面、表单、接口、服务和数据模型。
4. 实际运行、截图、接口调用、测试结果和构建结果。

禁止把推测当事实写入活文档。

## 三、活文档职责

`业务流程清单.md` 只回答“业务应该怎么做”。

必须记录：

1. 场景名称。
2. 业务角色。
3. 入口位置。
4. 前置条件。
5. 操作步骤。
6. 预期结果。
7. 异常路径。
8. 业务规则。
9. 待确认项。

不得记录：

1. 一次开发过程流水账。
2. 具体测试命令堆砌。
3. 与业务无关的技术实现细节。

`场景实现核查台账.md` 只回答“现在代码实现到什么程度”。

必须记录：

1. 状态：未核查、未实现、部分实现、已实现、已阻断。
2. 主要证据：文件、接口、页面、测试、截图或运行结果。
3. 剩余缺口。
4. 本轮验证结果。
5. 待确认项。
6. 下一步优先级。

不得记录：

1. 没有证据的“已完成”。
2. 与当前场景无关的大范围总结。
3. 可被代码或测试结果推翻的旧状态。

`控件交互逻辑说明.md` 只回答“用户在界面上能看见什么、点什么、得到什么反馈”。

必须记录：

1. 页面。
2. 弹框。
3. 控件。
4. 按钮。
5. 筛选项。
6. 表格列。
7. 提示文案。
8. 禁用状态。
9. 校验规则。
10. 跳转逻辑。
11. 权限展示。

不得记录：

1. 不存在的控件。
2. 只在计划里出现、代码中尚未落地的按钮。
3. 未经运行或源码证据确认的交互。

## 四、适用场景

以下任务优先采用场景驱动开发：

1. 涉及真实岗位操作路径的功能。
2. 涉及多页面、多接口、多单据状态或跨端联动的功能。
3. 涉及权限、数据隔离、文件、金额、库存、审批、审计、导入导出等高风险能力。
4. 用户要求模拟实际工作流程、跑一遍业务场景、按真实用户使用方式完善程序。
5. 用户使用 `开qg` 触发工作场景准备。

以下任务通常不需要完整套用本范式：

1. 单个明确 bug 修复，且不影响业务流程。
2. 纯代码清理、格式化、命名调整或依赖修补。
3. 用户明确要求只回答问题、不修改代码。

## 五、项目适配清单

把本范式放入任意项目后，必须先补齐项目适配信息。适配信息可以写入项目总纲、AGENTS 文档、README 或本范式所在目录的项目说明。

项目适配信息至少包含：

```text
项目名称：
主要业务域：
默认开发范围：
默认排除范围：
后端技术栈：
前端技术栈：
移动端或客户端范围：
主要数据源：
认证与权限机制：
菜单或入口来源：
通用模块清单：
业务流程文档路径：
实现核查台账路径：
控件交互说明路径：
规划文档路径：
测试与构建命令：
上线或交付边界：
```

项目适配信息优先级高于通用范式，但不得破坏范式的核心原则：先场景、再承载点、再实现、再验证、再同步文档。

## 六、承载点优先决策链

用户给出明确工作场景后，禁止默认新建模块。必须先按以下顺序判断实现方式：

1. 已有相关模块和对应功能，且功能能够满足目标：复用已有功能，只做必要验证、缺陷修复或交互整理。
2. 已有相关模块和对应功能，但功能达不到目标：补全已有功能，优先补齐校验、状态流转、权限、接口、页面控件、异常提示、测试和文档。
3. 已有相关模块，但缺少对应功能：在原模块新增功能入口、权限、接口、服务、页面、类型和必要测试。
4. 没有可承载的相关模块：才允许新建模块，并补齐模型、接口、服务、权限、菜单、页面、类型、测试和文档。

判断相关模块时，必须检查：

1. 业务域是否一致。
2. 数据对象是否一致或可复用。
3. 操作路径是否属于同一岗位流程。
4. 权限、菜单、数据隔离和通用模块是否已有承载点。
5. 项目适配清单中是否存在暂停开发、禁止修改或特殊保护边界。

每轮实施方案必须明确：

```text
实现类型：复用已有功能 / 补全已有功能 / 原模块新增功能 / 新建模块
判断依据：
不采用其它路径的原因：
```

如果无法判断是否已有承载模块，必须先检索代码和文档；仍无法判断时标注 `[待确认]`，不得直接新建模块。

## 七、场景定义模板

每轮场景开始前，必须形成以下信息。能从代码、文档或测试数据中确认的，先自行读取确认；不能确认的，标注 `[待确认]` 并说明原因。

```text
场景名称：
业务角色：
所属数据范围：
初始数据：
入口位置：
操作步骤：
预期页面结果：
预期接口结果：
预期数据结果：
权限边界：
异常路径：
验证方式：
本轮禁止事项：
待确认项：
```

字段要求：

1. `场景名称` 必须是一句话，包含角色和动作。
2. `业务角色` 必须对应真实岗位、真实用户类型或系统角色。
3. `所属数据范围` 必须写明是否涉及租户、组织、账套、项目、空间、门店、仓库、客户或其它隔离边界。
4. `初始数据` 必须列出完成场景所需的最小数据。
5. `入口位置` 必须能对应真实页面、菜单、命令、API、任务入口或客户端入口。
6. `操作步骤` 必须按用户实际点击、输入、提交、查看结果的顺序描述。
7. `权限边界` 必须同时覆盖展示控制和后端授权。
8. `异常路径` 至少覆盖 1 条失败路径；涉及资金、库存、审批、文件、权限、删除或外部系统时至少覆盖 2 条失败路径。
9. `验证方式` 必须写明使用人工检查、单元测试、接口测试、端到端测试、截图、文件校验或安全检查中的哪几类。
10. `本轮禁止事项` 必须写明不属于本场景的模块、端、数据和重构范围。

## 八、执行流程

每轮场景按以下顺序执行：

1. 读取项目总纲、项目适配信息、三份活文档和目标模块现有实现。
2. 检查已有模块、已有功能和可复用通用能力，确定实现类型。
3. 识别本轮涉及的接口、服务、模型、权限、菜单、页面、组件、类型、客户端和测试。
4. 输出最小实施方案，列出准备新增或修改的文件。
5. 按场景先跑通主路径，再检查异常路径。
6. 发现问题后只修复本场景必要范围。
7. 修改后执行与风险匹配的验证。
8. 同步维护三份活文档。
9. 输出结果、已验证内容、残余风险和下一轮建议。

涉及多个单据、多端联动、数据模型变更或高风险生产链路时，必须拆成可独立验收的阶段，并把规划文档放到项目约定的规划目录。

## 九、三层检查法

场景驱动开发必须同时使用三层视角检查：

1. 用户视角：入口是否找得到，表格、表单、弹框、提示、加载、空状态、失败反馈是否符合真实操作习惯。
2. 测试视角：字段校验、权限拒绝、重复提交、数据隔离、登录失效、并发提交、分页筛选、异常数据是否可控。
3. 开发视角：分层是否清晰，服务边界是否正确，事务或一致性是否足够，类型是否同步，是否复用已有通用模块。

任一视角发现的缺陷都要落到具体文件、接口、页面、控件、数据或业务规则；不能只写“体验不好”“需要优化”。

## 十、文档同步矩阵

每次场景开发必须按以下矩阵同步文档：

| 变化类型 | 必须同步的文档 |
|---|---|
| 新增、删除或调整业务步骤 | `业务流程清单.md` |
| 新增、删除或调整岗位、角色、入口、前置条件、异常路径 | `业务流程清单.md` |
| 确认某场景已实现、部分实现、未实现或被阻断 | `场景实现核查台账.md` |
| 新增证据文件、测试结果、构建结果、截图或运行结论 | `场景实现核查台账.md` |
| 新增、删除或编辑页面、弹框、控件、按钮、筛选项、表格列、提示文案、禁用状态、校验规则、跳转逻辑、权限展示 | `控件交互逻辑说明.md` |
| 范式模板、执行步骤、验收标准、禁止事项或同步规则变化 | `场景驱动开发范式.md` |

同步规则：

1. 只改发生变化的章节，禁止无原因整文件重写。
2. 文档必须和代码、运行结果或用户确认的业务事实一致。
3. 旧结论被新证据推翻时，必须更新状态并说明新证据。
4. `[待确认]` 项在确认前不得写成已实现规则。

## 十一、验证矩阵

按场景风险选择验证方式，不要求每轮全部执行，但跳过高相关验证时必须说明原因。

1. 后端接口或服务变化：运行相关后端测试；没有测试时补充最小测试或说明阻塞。
2. 权限变化：检查权限定义、接口授权、页面展示控制和角色分配入口。
3. 前端页面变化：运行类型检查、测试或构建；涉及布局、弹框、复杂表格时使用截图检查。
4. 真实点击流程变化：优先跑端到端流程，覆盖登录、入口、提交、失败提示和结果查看。
5. 文件、打印、导入导出变化：校验关键字段、数量、金额、中文字符、分页、下载和权限。
6. 数据隔离变化：检查租户、组织、项目、账套、门店、仓库或其它隔离字段。
7. 移动端或客户端变化：检查统一请求封装、认证、数据隔离、登录失效清理和安装包体积或分发影响。
8. 高风险生产链路变化：检查备份、回滚、发布步骤、健康检查和可追溯记录。

## 十二、待确认项规则

遇到以下情况必须标注 `[待确认]`，并暂停对应业务规则的实现：

1. 状态流转不明确。
2. 金额、库存、账务、权限、审批、删除、覆盖、回滚等强一致性规则不明确。
3. 权限粒度不明确。
4. 数据隔离边界不明确。
5. 批量操作或不可逆操作缺少确认口径。
6. 外部系统、第三方服务或人工流程边界不明确。

允许在待确认项存在时继续做的工作：

1. 阅读代码和文档。
2. 补充规划文档。
3. 修复与待确认规则无关的明确 bug。
4. 添加不会锁死业务规则的防御性校验或测试。
5. 完善活文档中的事实证据和待确认说明。

## 十三、输出要求

每轮结束时，结果说明必须包含：

1. 本轮模拟的场景名称。
2. 实现类型。
3. 判断依据和不采用其它路径的原因。
4. 修改或新增的文件。
5. 已同步的活文档。
6. 已验证的主路径和异常路径。
7. 执行过的测试、构建、截图、文件校验或安全检查。
8. 未执行验证的原因。
9. 残余风险和下一轮建议。

如果没有改代码，也必须说明读了哪些关键文件、发现了什么问题、建议下一轮如何拆分。

## 十四、禁止事项

1. 禁止把一个线程扩散成多个互不相关的业务场景。
2. 禁止为了跑通场景临时绕过权限、数据隔离、服务层校验或事务一致性。
3. 禁止只修表面显示而不定位接口、数据、编码或权限根因。
4. 禁止在未确认业务规则时自行发明状态流转、财务规则、库存规则、审批规则或删除规则。
5. 禁止用新建第二套相似模块替代已有模块或通用能力。
6. 禁止在未证明没有承载模块前新建模块。
7. 禁止把未验证的推测写成事实。
8. 禁止用整文件重写掩盖局部变更，除非用户明确要求替换模板或重建文档。

## 十五、迁移到新项目的步骤

在新项目中使用本范式时，按以下顺序执行：

1. 放入 `场景驱动开发范式.md`。
2. 填写项目适配清单。
3. 创建或映射三份活文档。
4. 从现有文档、代码入口和用户说明生成业务流程清单初稿。
5. 从业务流程清单生成场景实现核查台账初稿，状态默认为 `未核查`。
6. 从页面、路由、菜单、命令或客户端入口生成控件交互说明骨架，无法确认的控件标注 `[待确认]`。
7. 后续每次用户输入 `开qg`，按准备态确认卡片进入场景驱动开发。
